# PART 1. 원리: 경험이 아니라 "장면"이 달라집니다

## 1-1. 세 회사의 서류는 서로 다른 질문을 던집니다

| 회사 | 서류가 던지는 질문 | 문항 구성과 직무 설명 |
|---|---|---|
| **램리서치** | **"고객 Fab에서 오래 버티고, 처음 만나는 사람들과 일하며, 바뀌는 절차에 적응하면서 손으로 문제를 좁힐 사람인가?"** | 5문항 모두 400자: ① 하드웨어 실습 ② 육체적·정신적으로 힘들었던 경험과 극복 ③ 처음 만나는 사람들과 신뢰 쌓기 ④ 가장 오래 몰입한 활동 ⑤ 새로운 시스템·절차 수용. **지원동기 문항이 없습니다.** 직무 설명: "업무 대부분의 시간을 고객사의 팹에서 보내기 때문에 정신적·체력적 측면에서 자기관리가 중요" |
| **AMAT** | **"회사와 직무를 정확히 이해하고, 기준을 세워 문제를 분석하며, 맡은 결과를 끝까지 책임지는가?"** | ① 회사·CE 지원동기(1,000자) ② CE로서의 강점과 경험(1,000자) ③ 가장 복잡한 문제와 **분석 기준·접근**(800자) ④ 책임감, **맡은 역할과 실제 행동** 중심(800자). CE 공식 정의: "Applied's direct liaison with customers" |
| **TEL** | **"우리 가치(Values)대로 일할 사람인가?"** | 4문항 각 600자. ① 지원 계기 + 산업·직무 이해도 ② Awareness ③ Ownership + Teamwork(성과·배움까지) ④ Challenge + Pride(TEL 경력에서의 발휘까지) |

**문항 구성에서 읽히는 것**
- **램리서치는 다섯 문항 중 네 개가 "사람"을 묻습니다.** 체력·멘탈(②), 처음 보는 사람과의 신뢰(③), 지속성(④), 변화 수용(⑤)입니다. 고객 Fab에 상주하며 처음 만나는 고객 엔지니어와 일하고, 코봇·데이터 기반 정비처럼 바뀌는 절차를 받아들여야 하는 FSE의 현실이 그대로 문항이 됐습니다.
- **AMAT은 "어떤 기준으로"와 "실제로 취한 행동"을 문항에 직접 적었습니다.** 결과보다 **판단 과정과 본인 행동**을 보겠다는 뜻입니다. 기준을 첫째·둘째처럼 명시하고, "우리"가 아니라 "제가"로 쓰세요.
- **TEL은 문항 안에서 "성과나 배움", "TEL에서의 경력에 어떻게 발휘"까지 요구합니다.** 경험으로 끝내지 말고 마지막 2~3문장을 TEL 현장으로 연결해야 합니다.

## 1-3. 모든 버전에 공통으로 들어가야 하는 골격

어느 회사 버전이든 아래 골격 중 빠지는 단계가 없어야 합니다. 회사마다 달라지는 것은 **각 단계에 주는 분량**입니다.

> **문제 정의 → 진단(근거 데이터) → 조치 → 검증 → 재발 방지·표준화 → 직무 연결**

| 단계 | 빠지면 이렇게 읽힘 | 램리서치 비중 | AMAT 비중 | TEL 비중 |
|---|---|---|---|---|
| 문제 정의 | 무엇이 문제였는지 모름 | 짧게 | 보통 | 보통 (도전의 크기를 보여 줘야 함) |
| 진단 근거 | "감으로 고쳤다" | **가장 큼** | 큼 | 보통 |
| 조치 | — | 보통 | 보통 | 보통 |
| 검증 | "고친 것 같다" | 큼 | 보통 | 짧게 |
| 재발 방지·표준화 | "운 좋게 해결했다" | 보통 | 큼 (문서·공유) | **큼 (Pride의 근거)** |
| 소통·협업 | — | 짧게 | **가장 큼** | 큼 (Teamwork 문항) |
| 직무 연결 | "왜 우리 회사인지 모름" | 한 문장 | 한 문단 (직무 정의) | 한 문장 + 가치 단어 |

# PART 2. 도구: 경험을 "장면 카드"로 쪼개기

## 2-1. 장면 카드란

경험 하나를 처음부터 끝까지 이야기로 기억하면 회사마다 다르게 쓰기 어렵습니다. 대신 경험을 **8개의 장면**으로 쪼개 메모해 두면, 회사와 문항마다 필요한 장면만 골라 조립할 수 있습니다.

| 카드 | 적을 내용 | 주로 쓰는 곳 |
|---|---|---|
| **① 증상** | 무엇이 언제부터 어떻게 이상했나 (숫자로) | 3사 공통 첫 문장 |
| **② 원인 후보** | 무엇을 의심했고, 왜 그걸 의심했나 | 램리서치 |
| **③ 진단 근거** | 어떤 데이터·측정으로 후보를 지웠나 | **램리서치**, AMAT |
| **④ 조치와 검증** | 무엇을 바꿨고, 어떻게 확인했나 (반복 횟수, 전후 수치) | 3사 공통 |
| **⑤ 재발 방지** | 무엇을 남겼나 (점검표, 절차, 규칙) | AMAT, **TEL(Pride)** |
| **⑥ 소통** | 누구에게 무엇을 언제 공유했나, 오해나 누락은 없었나 | **AMAT** |
| **⑦ 협업** | 누구와 어떻게 나눠 했나, 내가 책임진 부분은 어디까지인가 | **TEL(Ownership·Teamwork)** |
| **⑧ 도전·감정** | 왜 굳이 그 일을 했나, 힘들었던 점, 자부심을 느낀 순간 | **TEL(Challenge·Pride)**, 램리서치(회복·몰입) |

> 💡 카드 ⑥⑦⑧은 경험 당시에 기록해 두지 않으면 나중에 기억이 나지 않습니다. 가장 먼저 적어 두세요.

## 2-2. 장면 카드 → 회사·문항 배치표

| 회사 · 문항 (분량) | 중심 카드 | 첫 장면 |
|---|---|---|
| **램리서치 ① 하드웨어 실습** (400) | ① → **②③** → ④ → ⑤ 한 줄 | 증상 |
| **램리서치 ② 육체적·정신적으로 힘들었던 경험** (400) | **⑧** + 극복을 위한 반복 행동 | 무엇이 왜 힘들었나 |
| **램리서치 ③ 처음 만나는 사람들과 신뢰** (400) | **⑥⑦** + 반복해서 지킨 작은 약속 | 낯선 사람들 속의 나 |
| **램리서치 ④ 가장 오래 몰입한 활동** (400) | 기간·횟수 + 방식의 변화 + 배운 점 | 몰입의 시작 |
| **램리서치 ⑤ 새로운 시스템·절차 수용** (400) | 처음의 생각 → 직접 써 본 행동 → 결과 → **⑥ 주변 전파** | 바뀐 시스템과 나의 첫 반응 |
| **AMAT ① 회사·CE 지원동기** (1,000) | 경험 1개(① ③ ④ 요약) + 회사 고유 근거 + CE 이해 | 지원을 결심하게 한 장면 |
| **AMAT ② CE로서의 강점** (1,000) | 강점 1~2개 선언 → ①~⑤ + **⑥** | 강점 선언 |
| **AMAT ③ 가장 복잡한 문제, 분석 기준** (800) | ① → **② + 분석 기준을 첫째·둘째·셋째로** → ③ → ④ → ⑤ | 왜 복잡했나 |
| **AMAT ④ 책임감, 역할과 실제 행동** (800) | **맡은 역할 → 목표 → 실제 행동(①~⑤)** → ⑦ | 내 역할 |
| **TEL ① 지원 계기 + 산업·직무 이해** (600) | 계기 장면 + 산업 이해(회사 수치) + 직무 이해 | 계기 |
| **TEL ② Awareness** (600) | 약점 자각 → 사건 → 개선 행동 → 달라진 습관 | 나의 약점 |
| **TEL ③ Ownership + Teamwork** (600) | **⑦**: 내가 책임진 부분과 팀이 함께 만든 부분 + 성과·배움 | 내 역할과 팀 상황 |
| **TEL ④ Challenge + Pride** (600) | **⑧** → ③ → ④ → **⑤** + TEL 경력에서의 발휘 | 도전의 이유 |

## 2-3. 소재를 고를 때의 기준

**경험의 "격"보다 장면 카드가 몇 장 채워지는지가 중요합니다.** 인턴 경험이라도 ③진단 근거와 ⑤재발 방지 카드가 비어 있으면 약한 소재입니다. 반대로 아르바이트 경험이라도 카드 8장이 다 채워지면 강한 소재가 됩니다(PART 4 사례 E).

| 티어 | 예 | 쓰는 법 |
|---|---|---|
| 1티어 | 학부연구생·연구실, 인턴, 현업 참여 | 하드웨어·문제 해결 문항의 핵심 증거 |
| 2티어 | 공정 실습, 공모전, 캡스톤, 동아리 프로젝트 | 협업·책임감 문항, 또는 장면 카드가 충분하면 핵심 문항에도 |
| 3티어 | 교육 수강, 부트캠프 | **단독 사용 금지.** 측정값·실험·문서 결과물을 덧붙여 보강 |

# PART 3. 회사별 변환 규칙

## 3-1. 램리서치 FSE / Data Analytics FSE (5문항 × 400자)

| 문항 | 규칙 |
|---|---|
| **① 하드웨어 실습** | 리듬: 제목 1줄 → 증상 1문장 → 의심한 부품·조건 1문장 → 측정·검증 1~2문장 → 원인과 조치 1문장 → 결과(숫자) + 재발 방지 1문장 → FSE 연결 1문장. 글로벌 FSE 직무기술서의 핵심 문장은 "isolate issues to the component level"(문제를 부품 단위까지 좁힘) |

## 사례 A. 학부 연구실: PECVD 증착 장비의 막 두께 편차 문제

### 경험 원재료

학부연구생으로 연구실 PECVD를 사용해 SiN 증착 실험을 진행했다.

어느 날 레시피를 바꾸지 않았는데도 웨이퍼 중심과 가장자리의 두께 편차가 기존 3% 수준에서 9%까지 커졌다. 장비를 사용하는 연구원 6명의 실험 일정에도 영향을 주기 시작했다.

원인 후보를 샤워헤드, MFC, 히터로 나누고 49포인트 두께 맵, MFC 설정·실측값, 히터 로그를 비교했다. 그 결과 외곽 히터 존의 온도가 설정값보다 6도 낮은 것을 확인했다.

담당자와 점검한 뒤 열전대 체결 상태를 조정했고, 이후 10장 연속 증착에서 두께 편차가 3.2% 수준으로 회복되는 것을 확인했다. 점검 결과는 사용자들과 공유했고, 이후 주간 점검표에 존별 온도 편차 확인 항목을 추가했다.

### 같은 경험에서 회사마다 무엇을 꺼낼까?

| 회사·문항 | 앞에 세울 장면 | 보여줘야 할 것 |
|---|---|---|
| **램리서치 FSE** ① 하드웨어 | 두께 편차를 원인별로 좁힌 과정 | 진단 방식 |
| **AMAT CE** ② 강점 | 장비 문제와 사용자 일정이 함께 영향을 받은 상황 | 진단 + 상황 공유 |
| **TEL FE** ④ Challenge + Pride | 업체 점검을 기다리기 전 할 수 있는 점검부터 시작한 장면 | 도전 이유 + 남긴 변화 |

같은 "두께 편차 3% → 9%"라는 사실을 쓰더라도 글의 중심은 달라야 합니다.

### ① 램리서치 FSE: Hardware 실습 경험

**이 문항에서 보여줄 것**

이 경험에서는 장비에 문제가 생겼을 때 **어떻게 원인을 쪼개고 좁혔는지**가 핵심입니다. 단순히 "PECVD를 사용해 봤다"보다, **어떤 증상을 봤고 → 어떤 가능성을 세웠고 → 무엇을 측정해 후보를 지웠는가**가 보여야 합니다.

**추천 흐름**

이상 현상 → 원인 후보 → 확인 순서를 정한 이유 → 측정 → 원인 특정 → 검증

**부분 예시**

> 학부연구생으로 PECVD를 사용하던 중 같은 레시피에서도 웨이퍼 가장자리의 두께가 얇아지며 편차가 3%에서 9%까지 커졌습니다. 레시피 변경이 없었다는 점에서 공정 조건보다 장비 상태를 먼저 확인했습니다. 샤워헤드, MFC, 히터를 원인 후보로 나눈 뒤 MFC 실측값과 49포인트 두께 맵을 비교했고, 가장자리에서만 편차가 반복되는 것을 확인했습니다. 이에 히터 로그를 추가로 확인해 외곽 존의 온도가 설정값보다 낮다는 단서를 찾았습니다.

**여기서 중요한 점**

"PECVD 경험이 있다"가 아니라 **"어떤 순서로 원인을 좁혔는가"** 가 주인공이어야 합니다. 마지막에 억지로 "부품 단위까지 원인을 찾는 FSE가 되겠습니다."를 붙이지 않아도 됩니다. 글 안에서 이미 진단 방식이 충분히 드러났다면 경험의 결과로 끝내도 좋습니다.

### ② AMAT CE: Customer Engineer로서의 강점

**이 문항에서 보여줄 것**

같은 경험이지만 이번에는 장비 진단만 쓰면 부족합니다. CE의 강점으로 가져가려면 **장비를 복구하는 과정 + 그 장비를 사용하는 사람에게 상황을 전달한 과정**이 함께 보여야 합니다.

**추천 흐름**

강점 → 문제가 사용자에게 미친 영향 → 내가 한 판단 → 진단 행동 → 상황 공유 → 결과

**부분 예시**

> 장비 점검이 길어지면서 다른 연구원들의 실험 일정까지 함께 밀리고 있었습니다. 저는 원인을 찾는 것만큼 점검 상황을 공유하는 것도 필요하다고 판단했습니다. 현재 확인 중인 항목과 다음 점검 시점을 사용자들에게 전달하고 예약 일정을 다시 조정한 뒤 원인 진단을 진행했습니다. 49포인트 두께 맵과 히터·MFC 로그를 비교해 외곽 히터 존의 이상을 좁혔고, 조치 후 반복 증착으로 두께 편차가 기존 수준으로 회복되는 것을 확인했습니다.

**이어서 쓸 내용**

마지막에는 "이 경험 이후 문제를 해결하는 것과, 문제 상황을 함께 겪는 사람이 같은 정보를 갖도록 만드는 것을 한 과정으로 보고 있습니다."처럼 **내가 갖게 된 업무 기준**으로 마무리할 수 있습니다.

### ③ TEL FE: Challenge + Pride

**이 문항에서 보여줄 것**

TEL 버전에서는 진단 기술 자체보다 **왜 굳이 먼저 움직였는가 → 무엇을 시도했는가 → 무엇을 남겼는가**가 더 중요합니다.

**추천 흐름**

**부분 예시**

**Pride를 쓰는 방법**

"문제를 해결해서 뿌듯했다"로 끝내지 않습니다. 이 경험에서는 "이후 제가 정리한 점검 항목이 주간 점검표에 추가돼 다른 연구원들도 같은 기준으로 장비를 확인하게 됐습니다."가 Pride의 근거입니다.

### 사례 A 비교

- **램리서치**: 어떻게 원인을 좁혔는가
- **AMAT**: 원인을 좁히면서 사용자에게 어떻게 상황을 공유했는가
- **TEL**: 왜 먼저 움직였고, 그 결과 무엇을 남겼는가

같은 장면을 회사 이름만 바꿔 쓰는 것이 아니라, **경험에서 꺼내는 의미가 달라져야** 합니다.

## 사례 B. 캡스톤: 특정 고도에서 흔들리는 드론

### 경험 원재료

4인 팀 캡스톤 프로젝트에서 쿼드콥터 하드웨어를 담당했다.

기체가 특정 고도에서만 좌우로 흔들리는 문제가 발생했다. 팀은 제어 게인 문제로 판단해 일주일간 PID를 조정했지만 증상이 사라지지 않았다.

문제를 모터·ESC·IMU로 다시 나누어 확인했다. IMU를 교체했지만 같은 문제가 나타났고, 비행 중 모터별 전류를 로깅한 결과 3번 모터의 리플만 다른 모터보다 약 2배 높았다.

ESC-모터 커넥터의 납땜 불량을 찾아 재작업했고, 이후 같은 조건에서 10회 반복 비행해 문제가 사라진 것을 확인했다. 소프트웨어 담당과 로깅 코드를 함께 만들고, 팀원들과 교대로 실험을 진행했다.

### 회사별 핵심

| 회사·문항 | 앞에 세울 장면 | 핵심 |
|---|---|---|
| **램리서치 FSE** ① | PID 조정으로 해결되지 않은 이후 원인을 다시 나눈 장면 | 진단 |
| **AMAT CE** ④ | 발표 3주 전 목표를 포기할지 결정해야 했던 상황 | 책임감 |
| **TEL FE** ③ | HW·SW 담당이 같은 데이터를 보도록 만든 과정 | Ownership + Teamwork |

### ① 램리서치 FSE

**추천 흐름**

증상 → 기존 가설 실패 → 원인 재분류 → 측정 → 부품 수준 원인 확인 → 검증

**부분 예시**

> 쿼드콥터가 특정 고도에서만 흔들리자 처음에는 제어 게인 문제라고 판단했습니다. 하지만 PID를 조정해도 증상이 반복돼 원인을 모터·ESC·IMU로 다시 나눴습니다. IMU 교체 후에도 문제가 같아 센서 문제를 제외했고, 모터별 전류를 측정하자 3번 모터의 리플만 약 2배 높았습니다. 이를 바탕으로 ESC와 모터 사이 연결부를 확인해 납땜 불량을 찾았습니다.

**좋은 포인트**

처음 가설이 틀렸다는 사실을 숨기지 않습니다. 오히려 **가설이 틀렸을 때 어떻게 다음 판단을 했는지**가 문제 해결력을 보여 줍니다.

### ② AMAT CE: 책임감을 가지고 목표한 결과를 만든 경험

**이 문항에서 보여줄 것**

책임감 문항은 단순히 "끝까지 했다"가 아닙니다. **어떤 목표를 내가 책임졌고, 포기할 수 있는 상황에서 왜 목표를 유지하기로 했는지**가 보여야 합니다.

**추천 흐름**

내 역할·목표 → 목표를 낮추자는 상황 → 내가 내린 판단 → 필요한 사람을 움직인 행동 → 결과

**부분 예시**

> 발표를 3주 앞두고도 특정 고도에서의 흔들림을 해결하지 못하자 저고도 비행만 시연하자는 의견이 나왔습니다. 하지만 고도 제어가 프로젝트의 핵심 목표였기 때문에 이를 포기하면 결과물을 완성했다고 보기 어렵다고 판단했습니다. 하드웨어 담당인 제가 원인을 다시 나누어 확인하겠다고 맡았고, 소프트웨어 담당과 모터별 전류를 확인할 수 있는 로깅 코드를 만들었습니다.

**마무리 방향**

"책임감은 혼자 모든 일을 하는 것이 아닙니다."처럼 정의로 끝내기보다, "이후 일정이 촉박할수록 목표를 낮추기보다 문제를 더 작은 단위로 나누고, 필요한 사람과 데이터를 먼저 연결하는 방식으로 해결하고 있습니다."처럼 **내 행동 방식의 변화**로 끝내는 것이 좋습니다.

### ③ TEL FE: Ownership + Teamwork

**이 문항에서 보여줄 것**

내가 다 했다고 쓰면 Teamwork가 사라지고, 팀이 했다고 쓰면 Ownership이 사라집니다. 그래서 반드시 구분합니다.

- **내가 책임진 것**: 하드웨어 문제 재분류와 진단
- **함께한 것**: 로깅 코드 작성, 반복 비행
- **팀에 남은 변화**: 의견보다 데이터 먼저 확인

**부분 예시**

> 하드웨어 담당자로서 원인을 끝까지 확인하는 것은 제가 맡았지만, 혼자 점검하는 것보다 팀 전체가 같은 데이터를 보는 것이 빠르다고 판단했습니다. 소프트웨어 담당과 모터별 전류 로깅 코드를 만들고, 비행 실험은 팀원들과 교대로 반복했습니다. 그 결과 3번 모터에서만 다른 전류 패턴을 발견해 연결부의 납땜 불량을 찾을 수 있었습니다.

마지막에는 결과뿐 아니라 "이후 문제가 생기면 각자의 추측보다 측정 데이터를 먼저 공유하기로 팀의 문제 해결 방식을 바꿨습니다."까지 가면 **Teamwork가 살아납니다.**

## 사례 C. 반도체 공정 실습: 포토 공정의 패턴 들뜸

### 경험 원재료

8인치 반도체 공정 실습에서 포토 공정을 진행했다.

같은 레시피였는데 조원 5명 중 3명의 웨이퍼에서 패턴 들뜸이 발생했다. 처음에는 작업 숙련도 차이로 생각했지만, 동일 레시피인데 특정 인원에게만 문제가 생기는 점이 이상해 공정 기록을 다시 확인했다.

각 웨이퍼가 사용한 스핀코터와 핫플레이트 번호를 대조했고, 불량 웨이퍼가 모두 2번 스핀코터를 사용했다는 공통점을 찾았다. 강사에게 근거를 보여 주며 추가 측정을 요청했고, 2번 장비의 회전 속도가 설정 3,000rpm보다 낮은 약 2,700rpm임을 확인했다.

장비 보정 후 재진행한 웨이퍼에서는 같은 문제가 발생하지 않았다. 이후 공정 기록지에 장비 번호를 적는 항목을 추가하자는 의견이 반영됐다.

### 회사별 핵심

| 회사 | 역할 |
|---|---|
| **램리서치** | 장비 조건을 의심하고 원인을 좁힌 경험 |
| **AMAT** | CE 직무에 관심을 갖게 된 계기 |
| **TEL** | 트랙 장비와 직무에 관심을 갖게 된 계기 |

이 사례는 특히 **지원동기에서 경험을 얼마나 쓰느냐**가 중요합니다. 지원동기에서는 경험을 길게 풀지 않고 직무를 선택하게 된 계기로만 사용합니다.

### ① 램리서치 FSE

**추천 흐름**

결과 차이 발견 → 왜 장비를 의심했는가 → 기록 대조 → 측정 → 결과

**부분 예시**

> 같은 레시피로 진행한 포토 공정에서 일부 웨이퍼에만 패턴 들뜸이 반복됐습니다. 작업자의 손기술 차이로 보기에는 같은 장비를 거친 웨이퍼끼리 결과가 유사하다는 점이 이상했습니다. 사용한 장비 번호를 다시 대조한 결과 불량 웨이퍼가 모두 2번 스핀코터를 거쳤고, 추가 측정에서 실제 회전 속도가 설정값보다 낮다는 것을 확인했습니다.

### ② AMAT CE: 지원동기

**작성 원칙**

지원동기에서 경험은 전체의 주인공이 아닙니다. **경험 → 직무 관심 → 회사 선택 기준 → Applied 선택 → 성장 방향**으로 넘어가야 합니다.

**경험 부분 예시**

> 같은 레시피인데도 장비 상태에 따라 공정 결과가 달라지는 것을 직접 확인하면서, 공정 조건을 설계하는 일만큼 장비가 정해진 성능을 지속적으로 내도록 관리하는 일이 중요하다는 것을 체감했습니다. 이 경험을 계기로 장비 상태를 현장에서 가장 가까이 확인하고 문제를 해결하는 CE 업무에 관심을 갖게 됐습니다.

**그다음에는?**

여기서 바로 기업 정보를 4~5개 나열하지 않습니다. **"내가 원하는 CE의 모습과 왜 Applied가 맞는가"** 를 연결할 회사 근거 1~2개만 씁니다. 회사 근거는 「현직자의 3사 심층 분석집」에서 가져오세요.

### ③ TEL FE: 지원 계기 + 산업·직무 이해

**작성법**

TEL도 비슷하지만, 문항이 산업과 직무 이해까지 직접 요구합니다. 따라서 **계기 → 산업/회사 이해 → FE 이해 → 나와의 접점**을 구분해 씁니다.

**계기 부분 예시**

> 포토 공정 실습에서 같은 레시피로 진행했는데도 장비별 회전 속도 차이 때문에 패턴 결과가 달라지는 것을 확인했습니다. 이 경험을 통해 노광 전후 공정에서 장비의 작은 편차를 관리하는 일이 패턴 품질에 직접 영향을 준다는 점에 관심을 갖게 됐습니다.

경험은 여기까지만 씁니다. 그다음부터 TEL의 트랙 장비와 FE 업무 이해로 넘어갑니다.

## 사례 D. 데이터 분석: 설비 진동 데이터로 고장 전조 찾기

### 경험 원재료

산학 프로젝트에서 공장 펌프 12대의 진동·온도 데이터를 이용해 고장 전조를 찾는 과제를 진행했다.

처음 만든 이상 탐지 모델은 하루 20건 이상의 경보를 발생시켰고, 현장 담당자가 얼마 지나지 않아 경보를 확인하지 않게 됐다.

경보 시점과 정비 기록을 대조한 결과 대부분이 기동 직후 약 30초 동안 발생하는 정상 진동이었다. 해당 구간을 분리하자 경보는 하루 3건 수준으로 감소했다.

남은 경보 가운데 한 설비에서 고주파 진동 증가가 2주 이상 이어지는 것을 발견해 현장 담당자와 확인했고, 베어링 윤활 부족을 찾아 조치했다. 이후 경보마다 현장 확인 결과를 함께 기록하는 방식으로 개선했다.

### 회사별 핵심

| 회사 | 경험에서 꺼낼 의미 |
|---|---|
| **램리서치 DA FSE** | 데이터로 이상을 좁히고 현장에서 검증 |
| **AMAT CE** | 데이터를 현장에서 쓸 수 있는 판단으로 바꿈 |
| **TEL Awareness** | 데이터만 믿고 현장을 보지 않았던 약점의 개선 |

### ① 램리서치 Data Analytics FSE

**부분 예시**

> 처음 만든 이상 탐지 모델은 하루 20건이 넘는 경보를 발생시켰습니다. 모델 성능을 높이기 전에 어떤 구간에서 경보가 발생하는지부터 확인했고, 정비 기록과 비교하자 대부분이 기동 직후 30초 동안 나타나는 정상 진동이었습니다. 해당 구간을 분리해 경보를 하루 3건으로 줄인 뒤, 남은 경보는 현장 담당자와 실제 설비 상태를 확인했습니다.

**핵심**

AI·모델 자체가 주인공이 아니라 **장비 문제를 좁히는 데 데이터를 어떻게 사용했는가**가 중요합니다.

### ② AMAT CE: 강점

**부분 예시**

> 제가 경험을 통해 갖게 된 강점은 데이터를 현장에서 실제로 사용할 수 있는 판단으로 바꾸는 것입니다. 첫 모델은 기술적으로는 동작했지만 하루 20건 넘는 경보 때문에 현장 담당자가 얼마 지나지 않아 결과를 보지 않게 됐습니다. 저는 모델을 더 복잡하게 만드는 대신, 경보가 언제 발생하는지와 실제 정비 이력을 하나씩 대조했습니다.

**이어지는 핵심**

**데이터를 만든 사람과 사용하는 사람이 같은 기준으로 판단하게 만든 행동**입니다.

### ③ TEL FE: Awareness

처음부터 "저의 약점은 OO입니다."라고 선언하지 않아도 됩니다.

**추천 흐름**

문제가 생긴 사건 → 내 행동의 문제 발견 → 약점 자각 → 개선 행동 → 현재 습관

**부분 예시**

> 이상 탐지 모델을 만든 뒤 성능 지표만 확인해 결과를 현장에 전달했습니다. 하지만 하루 20건이 넘는 경보가 반복되자 담당자는 얼마 지나지 않아 경보를 확인하지 않게 됐습니다. 그때 제가 데이터를 만드는 데 집중한 나머지, 실제 현장에서 결과가 어떻게 사용되는지는 충분히 확인하지 않았다는 점을 자각했습니다.

이후 개선 행동을 붙입니다. 이렇게 하면 **약점을 억지로 만들어 낸 느낌이 훨씬 줄어듭니다.**

## 사례 E. 비전공 현장 경험: 물류센터 야간조 자동 분류기

### 경험 원재료

대학 2학년 때 약 1년간 주 3회 물류센터 야간조로 근무했다.

자동 분류기 라인을 담당했고, 분류기가 멈추면 정비기사를 기다리는 동안 라인이 20분 이상 서는 경우가 있었다.

정비기사에게 기본 점검 방법을 배우고 근무 전 센서 오염과 벨트 상태를 점검하기 시작했다. 점검 결과를 기록해 자주 문제가 생기는 구간을 정리했고, 이후 야간조 공통 점검표로 확대했다.

한 번은 이상 사항을 교대 메모에 적었지만 다음 조가 확인하지 못해 라인이 약 40분간 멈춘 일이 있었다. 이후 이상 항목을 별도 한 장으로 정리하고 인수 여부를 확인하는 방식으로 바꿨다.

### 회사별 핵심

| 회사 | 강조점 |
|---|---|
| **램리서치** ② | 야간 근무와 학업 병행을 어떻게 관리했는가 |
| **AMAT** ④ | 내 행동이 다음 사람에게 전달되는 데까지 책임졌는가 |
| **TEL** ③ | 개인 점검을 팀의 기준으로 확장했는가 |

### ① 램리서치 FSE: 육체적·정신적으로 힘들었던 경험

**중요한 점**

힘든 일을 했다는 자랑이 아닙니다. 문항이 묻는 것은 세 가지입니다.

1. 무엇이 힘들었는가
2. 왜 힘들었는가
3. 어떻게 관리했는가

**부분 예시**

> 1년간 주 3회 야간 근무와 학업을 병행하면서 가장 어려웠던 것은 체력 자체보다 생활 리듬을 일정하게 유지하는 일이었습니다. 초반에는 야간 근무 다음 날 오전 수업까지 이어지며 학업 집중도가 떨어졌고, 이후 근무일과 비근무일의 일정을 다시 조정했습니다. 근무 다음 날 오전 수업을 최소화하고 과제와 시험 준비는 비근무일에 집중하는 방식으로 생활 패턴을 고정했습니다.

결과에서는 "결근 없이 버텼다"보다 **일정한 컨디션을 관리할 수 있게 된 변화**를 보여 주면 됩니다.

### ② AMAT CE: 책임감

이 사례에서 가장 좋은 장면은 **인수인계 실패**입니다.

**부분 예시**

> 벨트 장력 이상을 확인해 교대 메모에 남겼지만 다음 조가 이를 보지 못했고, 새벽에 라인이 약 40분간 멈췄습니다. 처음에는 필요한 정보를 남겼으니 제 역할은 다했다고 생각했습니다. 하지만 정보가 실제 다음 근무자에게 전달되지 않았다면 결과까지 책임진 것은 아니라고 판단했습니다. 이후 이상 항목을 별도 한 장으로 정리하고, 인수 여부를 직접 확인하는 방식으로 바꿨습니다.

이 장면은 "내가 책임감을 발휘했다"가 아니라 **책임의 범위를 어떻게 다시 정의하게 됐는가**를 보여 줍니다.

**마무리 예시**

> 이후에는 제가 행동을 끝냈는지가 아니라, 그 결과가 다음 사람에게 실제로 전달됐는지까지 확인하는 습관을 갖게 됐습니다.

### ③ TEL FE: Ownership + Teamwork

**추천 흐름**

내 라인의 문제 → 내가 먼저 시작한 행동 → 혼자서는 해결할 수 없는 한계 → 팀의 방식으로 확장 → 결과

**부분 예시**

> 처음에는 제 담당 라인의 정지만 줄이면 된다고 생각해 정비기사에게 기본 점검 방법을 배우고 근무 전 점검을 시작했습니다. 하지만 다른 조 시간에 같은 문제가 반복되면서 개인의 노력만으로는 라인의 정지를 줄일 수 없다는 한계가 보였습니다. 점검 기록을 정리해 자주 문제가 생기는 위치와 확인 순서를 한 장으로 만들고, 야간조 전체가 함께 사용하는 점검표로 바꾸자고 제안했습니다.

TEL에서는 이처럼 **Ownership이 Teamwork로 확장되는 과정**이 보여야 합니다.

## 사례 F. 석사 연구: ICP 식각 공정 선택비와 장비 상태

### 경험 원재료

석사 과정에서 ICP 식각으로 SiO₂/Si 선택비 15 이상을 목표로 연구했다.

기존 조건의 선택비는 9였다. RF source, bias, C4F8/Ar 유량비, 압력을 변수로 실험해 선택비 16 수준의 조건을 찾았다.

하지만 같은 조건에서도 주 초반과 후반의 식각률이 약 8% 차이 나는 문제가 반복됐다.

웨이퍼마다 챔버 클리닝 이후 경과 시간과 RF 반사 전력을 기록한 결과, 클리닝 직후 첫 3장에서만 반사 전력이 높고 식각률이 낮았다. 이후 더미 웨이퍼 3장을 이용한 시즈닝 절차를 추가해 주간 편차를 2% 이내로 줄였다.

### 회사별 핵심

| 회사 | 앞에 세울 것 |
|---|---|
| **AMAT CE** ③ | 공정 변수와 장비 변수를 나눈 분석 기준 |
| **TEL PE** ④ | 선택비 목표에 도전하고 재현성을 만든 과정 |
| **램리서치 FSE** ① | 공정 최적화가 아니라 장비 상태 변화 진단 |

공정 연구를 장비 직무에 사용할 때 가장 중요한 예시입니다.

### ① AMAT CE: 가장 복잡한 문제와 분석 기준

**이 문항에서 보여줄 것**

"16회 DOE를 했다"보다 **문제가 복잡할 때 어떤 기준으로 변수를 분리했는가**가 중요합니다.

**추천 흐름**

왜 복잡했나 → 분석 기준 → 기준에 따라 확인 → 원인 → 검증

**부분 예시**

> 같은 레시피를 사용했는데도 주 초반과 후반의 식각률이 약 8% 달라지는 문제가 반복됐습니다. 레시피 변수와 장비 상태가 함께 영향을 줄 수 있어, 두 요인을 동시에 바꾸면 원인을 판단하기 어렵다고 봤습니다. 그래서 먼저 바뀐 것과 바뀌지 않은 것을 구분했습니다. 레시피는 고정하고 웨이퍼별 클리닝 후 경과 시간과 RF 반사 전력처럼 시간에 따라 달라질 수 있는 장비 상태만 기록했습니다.

이어지는 내용에서 원인과 검증을 보여 줍니다.

**포인트**

반드시 "첫째, 둘째, 셋째"라고 쓸 필요는 없습니다. 분석 기준이 서로 구분되어 읽히면 충분합니다.

### ② TEL PE: Challenge + Pride

> ※ 이 예시는 PE 문항이 동일하게 출제된 경우를 가정한 작성 예시입니다. 실제 공고의 직무와 문항은 지원 시점에 다시 확인해야 합니다.

**작성법**

쉽지 않은 목표 → 기존 방식의 한계 → 새로운 접근 → 성과 → 재현 가능하게 만든 것 → Pride

**부분 예시**

> 기존 조건에서 선택비는 9 수준이었고, 목표인 15 이상을 만들기 위해 여러 변수를 한꺼번에 조정하던 방식으로는 원인을 구분하기 어려웠습니다. 저는 변수의 영향을 먼저 나누기 위해 부분요인설계를 적용했고, 바이어스 파워와 유량비의 상호작용을 확인해 선택비 16 수준의 조건을 찾았습니다. 하지만 같은 조건에서도 식각률 편차가 남아 있었기 때문에 최적값을 찾은 것으로 연구를 끝내지 않았습니다.

Pride는 **결과가 연구실 표준 조건으로 남아 다른 사람에게도 사용됐다**는 사실에서 가져옵니다.

### ③ 램리서치 FSE: 하드웨어 경험

**가장 중요한 변환**

석사 지원자가 흔히 하는 실수가 "DOE를 통해 선택비를 최적화했습니다."를 그대로 FSE 자소서에 쓰는 것입니다. FSE에서는 공정 최적화 장면을 덜어 내고 **장비가 평소와 다르게 동작했던 순간**을 가져옵니다.

**부분 예시**

> 같은 레시피인데도 주 초반과 후반의 식각률이 약 8%씩 달라지는 현상이 반복됐습니다. 공정 조건은 그대로였기 때문에 시간에 따라 달라질 수 있는 챔버 상태를 먼저 확인했습니다. 웨이퍼마다 클리닝 이후 경과 시간과 RF 반사 전력을 기록해 비교하자, 클리닝 직후 첫 3장에서만 반사 전력이 높고 식각률이 낮았습니다.

같은 석사 연구인데도 주인공이 달라집니다.

- **TEL PE**: 공정 성과
- **AMAT CE**: 문제 분석 기준
- **램리서치 FSE**: 장비 상태 진단

## 4-7. 같은 지원자의 문항 세트는 어떻게 구성할까?

하나의 경험을 세 회사에 반복해서 쓰는 것과, 한 회사 안에서 모든 문항에 같은 경험을 쓰는 것은 다릅니다. 보통 지원자가 가진 경험이 4~6개라면 **한 회사 안에서 같은 경험은 최대 1~2개 문항**에만 사용하고, 같은 경험을 쓰더라도 서로 다른 장면을 선택하는 것이 좋습니다.

### 램리서치 FSE 예시

| 문항 | 사용할 경험 | 핵심 장면 |
|---|---|---|
| ① Hardware | 사례 A 연구실 | PECVD 원인 진단 |
| ② 힘든 경험 | 사례 E 야간 근무 | 생활 리듬 관리 |
| ③ 신뢰 | 사례 E 야간 근무 | 정비기사와 작은 약속·기록 |
| ④ 몰입 | 별도 취미·프로젝트 | 장기간 반복과 방식의 변화 |
| ⑤ 새 시스템 | 사례 A 연구실 | 새로운 기록 시스템 수용 |

중요한 것은 다섯 문항 끝에 모두 "FSE가 되겠습니다."라고 쓰는 것이 아닙니다. 다섯 문항을 함께 읽었을 때 **진단 방식 / 현장 적응 / 신뢰 / 지속성 / 변화 수용**이라는 일관된 행동 특성이 보이면 됩니다.

### AMAT CE 예시

| 문항 | 추천 경험 |
|---|---|
| ① 지원동기 | 사례 C 공정 실습 |
| ② CE 강점 | 사례 A 또는 D |
| ③ 복잡한 문제 | 사례 F |
| ④ 책임감 | 사례 B 또는 E |

AMAT은 특히 네 문항의 역할을 구분하는 것이 중요합니다.

- ① 왜 Applied와 CE인가
- ② 내가 가진 직무 강점은 무엇인가
- ③ 어떤 기준으로 복잡한 문제를 분석하는가
- ④ 맡은 결과를 위해 실제로 어떻게 행동하는가

같은 문제 해결 경험을 네 번 반복하지 마세요.

### TEL FE 예시

| 문항 | 추천 경험 |
|---|---|
| ① 지원 계기·이해 | 사례 C |
| ② Awareness | 사례 D |
| ③ Ownership + Teamwork | 사례 B 또는 E |
| ④ Challenge + Pride | 사례 A |

TEL은 가치 단어 자체보다 **각 가치가 다른 행동으로 보이는지**를 점검해야 합니다. 예를 들어 모든 문항에서 "끝까지 포기하지 않았다"만 반복하면 Challenge, Ownership, Pride가 구분되지 않습니다.

| 가치 | 보여줄 것 |
|---|---|
| **Awareness** | 나를 어떻게 인식하고 바꿨는가 |
| **Ownership** | 어디까지 내 책임으로 보았는가 |
| **Teamwork** | 다른 사람과 어떤 방식으로 결과를 만들었는가 |
| **Challenge** | 왜 기존 방식과 다른 시도를 했는가 |
| **Pride** | 그 행동이 어떤 결과나 기준으로 남았는가 |

이렇게 나눠 생각하면 소재를 고르기 쉬워집니다.

### 정리: 경험은 하나여도, 주인공이 되는 장면은 달라집니다

같은 경험을 다르게 쓴다는 것은 표현을 바꾸는 것이 아닙니다. 같은 경험 안에도 문제 해결, 판단, 협업, 책임, 도전처럼 여러 장면이 있습니다.

회사가 달라질 때 바뀌어야 하는 것은 회사 이름이나 마지막 문장이 아니라, **어떤 장면을 먼저 보여 주는지, 그 장면에서 나의 어떤 판단을 보여 주는지, 그리고 그 경험을 어떤 의미로 해석하는지**입니다.

그래서 자기소개서를 쓰기 전에 먼저 경험을 충분히 나눠 두는 것이 중요합니다. 경험은 하나여도, 문항이 달라지면 주인공이 되는 장면은 달라집니다.

## 6-2. D-3 → D-day 공통 루틴

> 아래 루틴을 **회사마다 한 번씩** 돌립니다. 램리서치는 10/4~10/7, AMAT은 10/9~10/12입니다.

### D-3: 초안을 "완성"으로 선언하는 날

**목표: 모든 문항에 끝까지 쓴 글이 있는 상태로 만들기.** 이날 이후로는 소재를 바꾸지 않습니다.

| 시간 | 할 일 | 완료 기준 |
|---|---|---|
| 오전 | 문항별 소재 확정 | 문항마다 경험 1개가 정해지고, 한 회사 안에서 같은 경험이 2번을 넘지 않음 |
| 오후 | 빈 문항부터 끝까지 쓰기 | 모든 문항이 글자 수 제한의 90% 이상 채워짐 |
| 저녁 | 문항별 첫 문장만 모아서 읽기 | 첫 문장만 읽어도 무슨 경험인지, 어느 직무인지 보임 |

**D-3 체크리스트**
- [ ] 모든 문항에 초안이 있다
- [ ] 소재가 확정됐다 (이후 바꾸지 않는다)
- [ ] 글자 수 제한을 넘는 문항이 없다 (공백 포함 기준인지 사이트에서 확인)
- [ ] 첫 문장 모음만 읽어도 지원 직무가 보인다

> ⚠️ D-3에 "더 좋은 경험이 있을 것 같다"는 생각이 들어도 소재를 바꾸지 마세요. 소재를 바꾸면 D-2·D-1 점검을 처음부터 다시 해야 하고, 그 시간이 남지 않습니다.

### D-2: 사실과 숫자를 검증하는 날

**목표: 면접에서 "그게 정확히 무슨 뜻이죠?"라는 질문을 받아도 막히지 않을 글로 만들기.**

| 점검 | 방법 | 통과 기준 |
|---|---|---|
| **숫자 점검** | 글에 나온 숫자를 모두 표시 | 모든 숫자에 "어떻게 측정했는지" 한 문장으로 답할 수 있음. 추정치는 "약"을 붙임 |
| **골격 점검** | 경험 문단마다 6단계 표시 | 문제 정의 → 진단 근거 → 조치 → 검증 → 재발 방지 → 직무 연결 중 빠진 단계가 없음 |
| **회사 정보 점검** | 회사에 대해 쓴 문장을 모두 표시 | 출처를 댈 수 있음. 6-4의 틀리기 쉬운 정보에 해당하지 않음 |
| **직무 언어 점검** | 장비 계열(FSE·CE·FE)인지 공정 계열(PSE·PE)인지 확인 | 장비 계열 지원서에 "레시피 최적화", "공정 창" 같은 공정 계열 언어가 중심에 있지 않음 |
| **나 vs 팀 점검** | 팀 경험 문단에서 주어 확인 | "우리는"으로 끝나는 문장마다 "그중 내가 한 일"이 보임 |

**D-2 체크리스트**
- [ ] 문단마다 숫자가 1개 이상 있고, 모두 측정 방법을 설명할 수 있다
- [ ] 경험 문단에 진단 근거·검증·재발 방지가 모두 있다
- [ ] 회사 정보 문장에 출처가 있다
- [ ] 지원 직무의 언어로 썼다
- [ ] 팀 경험에서 내 역할이 분리돼 있다

### D-1: 소리 내어 읽고 최종본을 확정하는 날

**목표: 남이 읽어도 막히지 않는 글, 그리고 제출 직전에 손댈 곳이 없는 상태.**

| 시간 | 할 일 | 방법 |
|---|---|---|
| 오전 | **소리 내어 읽기** | 숨이 차서 끊기는 문장은 둘로 나눔. 같은 단어가 한 문단에 3번 이상 나오면 바꿈 |
| 오후 | **3초 테스트** | 지원동기(AMAT ①, TEL ①)에서 회사명을 경쟁사로 바꿔 읽어 봄. 그래도 자연스러우면 회사 고유 근거를 1개 넣음. 램리서치는 지원동기 문항이 없으므로 다섯 문항의 마지막 문장을 모아 읽고 FSE가 보이는지 확인 |
| 오후 | **회사명·직무명 검색** | 아래 검색어를 문서 전체에서 찾아 지원 회사 것만 남았는지 확인 |
| 저녁 | **최종본 저장과 백업** | 파일명에 날짜와 "최종"을 넣고, 클라우드와 로컬에 각각 저장 |
| 저녁 | **업로드 리허설** | 지원 사이트에 로그인해 입력 칸, 첨부 형식, 임시저장 여부를 미리 확인 |

**회사명·직무명 검색어**

> 램리서치 · Lam · LAM · 어플라이드 · Applied · AMAT · 도쿄일렉트론 · TEL · FSE · CE · FE · PSE · PE · FPE

**D-1 체크리스트**
- [ ] 소리 내어 읽으며 막히는 문장을 고쳤다
- [ ] 지원동기가 3초 테스트를 통과한다 (램리서치는 마지막 문장 모아 읽기)
- [ ] 다른 회사 이름과 직무명이 하나도 없다
- [ ] 최종본을 두 곳 이상에 저장했다
- [ ] 지원 사이트의 입력 형식과 첨부 형식을 확인했다

**자기소개서**
- [ ] 하드웨어 실습 문항이 **400자 이내**이고, **부품 단위로 원인을 좁힌 장면**이 보인다
- [ ] 400자 리듬: 증상 → 의심한 부품·조건 → 측정·검증 → 원인과 조치 → 결과 숫자 → FSE 연결
- [ ] **5문항 모두 400자 이내**다
- [ ] ② 힘들었던 경험: "힘들었던 **이유**"를 따로 분석했고, 극복이 **구체적 수단**(수면·운동·일정 재배치·도움 요청)이다
- [ ] ③ 신뢰: 친화력 자랑이 아니라 **반복해서 지킨 작은 약속과 정확한 기록**이 있고, 신뢰가 생긴 증거(상대의 행동 변화)가 있다
- [ ] ④ 몰입: **기간과 횟수**, 처음과 나중의 **방식 변화**, 배운 점이 있다
- [ ] ⑤ 새 시스템·절차: 처음 생각 → **직접 써 본 행동** → 결과(데이터) → 주변 전파 순서다
- [ ] 같은 경험을 2문항 넘게 쓰지 않았다
- [ ] 지원동기 문항이 없으므로, 다섯 문항의 **마지막 문장**을 모아 읽었을 때 "고객 Fab의 FSE"가 보인다
- [ ] "**공정을 최적화하고 싶다**"가 중심인 문장이 없다 (FPE와 혼동되어 읽힘)
- [ ] DA FSE라면 "모델 정확도"가 아니라 **"로그·센서 데이터로 이상을 좁히고 현장에서 확인한"** 장면이 앞에 있다

### AMAT (마감 10/12 월 17:00)

**지원 자격**

- [ ] 해외여행(출장) 결격 사유가 없다
- [ ] 지원 차수를 확인했다: 8/27~9/9 1차수(Application Engineer 등)는 **이미 마감**. 지금은 2차수

**제출 서류**
- [ ] 자사 양식 또는 국/영문 이력서를 준비했다
- [ ] 파일명을 공식 안내 규칙에 맞췄다 (예: "**포지션 타이틀_지원자 이름**". 공고 원문에서 확인)
- [ ] 이력서 첫 경험이 지원 직무와 바로 이어진다
- [ ] 영문 이력서라면 장비·공정 용어를 원어(PM, troubleshooting, DOE, uniformity 등)로 통일했다

**자기소개서**
- [ ] 분량: ①② **1,000자**, ③④ **800자** 이내다
- [ ] ① 지원동기: **회사 동기와 CE 직무 동기를 문단으로 나눴고**, 회사 고유 근거가 1~2개 있다. 회사 칭찬("AI 반도체 시대를 선도하는…")으로 시작하지 않는다
- [ ] ①② CE 이해에 3요소가 녹아 있다: 고객과 AMAT 사이의 기술 창구 / 설치·예방정비·트러블슈팅으로 가동률 유지 / 장비 데이터로 문제를 미리 좁힘
- [ ] ② 강점: **첫 문장에서 강점을 1~2개로 선언**하고 경험 하나로 증명했다
- [ ] ③ 복잡한 문제: 문항이 묻는 **"어떤 기준으로"**에 답했다. 분석 기준을 첫째·둘째·셋째로 명시했다
- [ ] ④ 책임감: 문항이 요구하는 **"맡은 역할"**을 먼저 밝히고, **"실제로 취한 행동"**을 "제가 ~했습니다" 문장으로 썼다. 결과가 숫자로 있다
- [ ] 석사 연구를 썼다면 공정 최적화(DOE)가 아니라 **장비 상태를 진단한 장면**을 앞에 세웠다 (CE는 장비 계열)

### TEL (공고 오픈 후 적용)

- [ ] 마감일과 시각 (공식 공고 기준)
- [ ] 모집 직무 (FE, PE, 데이터 등)
- [ ] 일본어 우대 기준 (신입 기준 JLPT N3 / JPT 500 수준이었음)

**자기소개서**
- [ ] 4문항 모두 **최대 600자** 이내다
- [ ] 문항마다 해당 가치(Awareness / Ownership + Teamwork / Challenge + Pride)를 **형용사가 아니라 행동으로** 증명했다
- [ ] ③에 문항이 요구하는 **"성과나 배움"**이 있다
- [ ] ④에 문항이 요구하는 **"TEL에서의 경력에 어떻게 발휘"**가 1~2문장 있다
- [ ] Q1에 **산업 이해와 직무 이해를 따로** 썼다
